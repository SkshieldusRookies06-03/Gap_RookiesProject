## 실제 백엔드 500 — 2026-11-09 시점 기록(당시 미검증 · 아래 2026-11-10 추가 참고)
점검서 방법 "500 유발 시 화면 문구"를 실제 서버로는 하지 못했다.
- 최초 점검: Docker 데몬 미기동.
- compose 기동 뒤(2026-11-09): 코드·DB를 바꾸지 않고 실제 500을 내는 승인된 방법이 없다.
  - backend common/GlobalExceptionHandler는 문서화된 오류 경로를 400·409·415·413·503 등으로 매핑하고, 500은 처리되지 않은 예외(Exception.class)뿐이다 — 스택은 로그에만, 응답 message는 null.
  - application.yml server.error.include-stacktrace: never · include-message: never (정적 확인).
  - 점검서·onboarding B-8 방법(깨진 JSON `{`으로 로그인)은 실제 백엔드에서 400 VALIDATION_ERROR — 500 재현이 아니므로 이 행의 500 검증으로 보지 않는다.
  - DB 컨테이너 중지·데이터 주입·코드 변경 등 임의로 500을 만드는 방법은 쓰지 않았다.
- 실제 백엔드 503(AI 중지) 화면도 이번에 실행하지 않았다 — 위 표의 503은 가로챈 응답(목 환경) 결과다.
→ B-8(T-063)에서 실제 오류 응답 본문에 스택이 없는지 확인하고, 실제 500 재현 방법은 기술 리드 승인 후 진행한다.

## 실제 백엔드 HTTP 500 응답 — 확인 (2026-11-10 · B-8 T-063 결과 인용)
근거: security/evidence/B-8.txt D · security/rows/FA.md B-8 행
- 환경: 개인 로컬 Docker Compose (nginx → backend → MariaDB) · 사용자 직접 실행
- 방법: 정상 로그인 → 개인 로컬 DB 일시 중지 → 유효한 Access Token으로 인증된 GET /api/documents (curl · 토큰 값 비기록)
- 시각: 2026-11-10 16:29:34 KST
- 응답: HTTP/1.1 500 · Content-Type: application/json
  {"success":false,"data":null,"message":"잠시 후 다시 시도해 주세요","timestamp":"2026-11-10T16:29:34.0101433+09:00","statusCode":500,"code":"INTERNAL_SERVER_ERROR"}
- 노출: 스택 트레이스·예외 클래스·SQL·DB 연결 정보·내부 경로 0 → B-8 PASS
- 프론트와의 관계(코드 기준 · 화면 실행 아님): ErrorMessage.jsx BY_CODE.INTERNAL_SERVER_ERROR = "잠시 후 다시 시도해 주세요" — 서버 message를 쓰지 않으므로
  실제 500 봉투도 위 표의 가로챈 500과 같은 경로로 렌더된다고 판단. 서버 응답 자체에도 노출할 내부 정보가 없다.

## 실제 브라우저 검증 (2026-11-10 KST · 사용자 실행)
환경: 개인 로컬 Docker Compose(nginx → 실제 backend → MariaDB) · Chrome DevTools Network(Preserve log · Disable cache)

A) DB 중지 후 /documents 새로고침 — 실제 500 화면 검증으로 인정하지 않음
- DB 정상: POST /api/auth/refresh 200 · GET /api/documents 200
- DB 중지 → /documents 새로고침
- POST /api/auth/refresh 약 30.02초 후 HTTP 500 · GET /api/documents 신규 요청 없음 · 프론트가 /login으로 이동
- 원인(코드 확인): 새로고침 직후엔 Access가 메모리에 없어 send() → ensureAccess()가 먼저 refresh를 부른다(frontend/src/api/client.js:69-73).
  refreshOrClear()(client.js:61-63)는 오류 종류와 관계없이 authStore.clear() → App.jsx Protected(:13-15)가 refreshToken 없음으로 /login 이동.
  그래서 문서 목록 요청 자체가 나가지 않았다 — 문서 목록 500 화면이 아니다.
- 참고: refresh fetch(client.js:43-47)에는 타임아웃이 없어 서버 응답(약 30초)을 끝까지 기다렸다.

B) 새로고침 없이 문서 필터 변경 — 네트워크 오류 UI 확인으로만 기록(실제 HTTP 500 화면 아님)
- DB 정상: 로그인 200 · 문서 목록 200
- 로그인 상태 유지 · 새로고침 없이 개인 로컬 DB 중지 → /documents의 "공고" 필터 클릭
- 새 GET /api/documents?... 요청 발생 → 약 10초 후 Network에 canceled
- 화면: "서버에 연결할 수 없습니다" + "다시 시도" 버튼 · 스택 트레이스·SQL·DB 주소·내부 경로 노출 없음
- 해석(확정 아님): 프론트 요청 타임아웃 10초(client.js TIMEOUT_MS · 초과 시 abort → NETWORK_ERROR)와 시간이 일치한다.
  정확한 취소 원인은 코드·추가 로그 확인 전까지 확정하지 않는다. 서버가 500을 돌려줬는지는 브라우저에서 관측되지 않았다.

## 별도 검토 사항 — FE-화면 담당(T-009 · frontend/src/api/client.js) · 기술 리드에게 전달 (F-7 판정과 별개 · 이번에 코드 수정 없음)
- refresh가 500·네트워크 오류로 실패해도 세션을 비워 로그인 화면으로 보낸다 — 401 인증 실패와 서버 장애를 구분하지 않음(refreshOrClear).
  SPEC §4.1(SPEC.md:103)은 refresh 실패를 401 INVALID_REFRESH_TOKEN으로 정의하고, §4.4(:158·:164)는 401 코드의 처리와 500의 사용자 표시 문구를 정의하지만,
  refresh 자체가 500·네트워크 오류로 실패할 때의 세션 처리 정책은 명시하지 않았다. docs/6 :117·:120·:136과 FS-FE화면.md:90도 "refresh 실패면 clear()"로만 적어 범위가 모호하다
  — 명세 간 확정적 충돌이 아니라 정책 공백·모호함.
- refresh fetch에 타임아웃이 없다(일반 요청은 10초).
- 장애 중 서버에서는 아직 유효한 refresh가 브라우저에서 지워져 복구 뒤 다시 로그인해야 한다 — 취약점은 아니고 가용성·사용성 문제. S-ID 여부는 기술 리드 판단.

## 브라우저에서 실제 500 표시 — 미검증
- curl로 실제 500 응답 본문만 확인했다. 실제 백엔드 500을 브라우저 화면(내 문서 목록 등)에서 띄워 문구·노출을 본 검증은 하지 않았다.
- 실제 백엔드 503(AI 중지) 화면도 여전히 미실행 — 위 표의 503은 가로챈 응답 결과.
- 재현 안내: DB 중지 방식으로 실제 HTTP 500 브라우저 표시를 재현하지 못함(2026-11-10 위 A·B — 새로고침은 refresh 500 → /login, 새로고침 없이 필터 변경은 약 10초 뒤 요청 취소).
  추가 검증은 기술 리드와 재현 방법을 협의한 후 진행.
