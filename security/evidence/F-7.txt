## 실제 백엔드 500 — 미검증
점검서 방법 "500 유발 시 화면 문구"를 실제 서버로는 하지 못했다.
- 최초 점검: Docker 데몬 미기동.
- compose 기동 뒤(2026-11-09): 코드·DB를 바꾸지 않고 실제 500을 내는 승인된 방법이 없다.
  - backend common/GlobalExceptionHandler는 문서화된 오류 경로를 400·409·415·413·503 등으로 매핑하고, 500은 처리되지 않은 예외(Exception.class)뿐이다 — 스택은 로그에만, 응답 message는 null.
  - application.yml server.error.include-stacktrace: never · include-message: never (정적 확인).
  - 점검서·onboarding B-8 방법(깨진 JSON `{`으로 로그인)은 실제 백엔드에서 400 VALIDATION_ERROR — 500 재현이 아니므로 이 행의 500 검증으로 보지 않는다.
  - DB 컨테이너 중지·데이터 주입·코드 변경 등 임의로 500을 만드는 방법은 쓰지 않았다.
- 실제 백엔드 503(AI 중지) 화면도 이번에 실행하지 않았다 — 위 표의 503은 가로챈 응답(목 환경) 결과다.
→ B-8(T-063)에서 실제 오류 응답 본문에 스택이 없는지 확인하고, 실제 500 재현 방법은 기술 리드 승인 후 진행한다.
