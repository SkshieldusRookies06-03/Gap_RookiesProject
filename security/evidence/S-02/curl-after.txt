## 3. 없는 계정은 잠기지 않고 401 (1~5회째는 가입 계정과 같은 응답 · 6회째부터 차이 → 아래 3-1 · 점검서 §7)
$ curl -s -X POST localhost:8080/api/auth/login -H 'Content-Type: application/json' -d '{"email":"nobody@example.com","password":"wrong"}'
{"success":false,"data":null,"message":"이메일 또는 비밀번호가 올바르지 않습니다","timestamp":"2026-11-09T15:28:02.882175672+09:00","statusCode":401,"code":"INVALID_CREDENTIALS"} HTTP 401

## 3-1. 계정 열거 확인 (2026-11-10 11:13 KST 추가 · kim·lee 대신 테스트용 가짜 계정)
$ curl -X POST localhost:8080/api/auth/register -d '{"email":"enum-test@example.com","password":"Passw0rd!","name":"enumtest"}'   → 201
$ (같은 오답 로그인 7회씩)
enum-test@example.com   (가입됨)    401 401 401 401 401 423 423
nobody-enum@example.com (가입 안 됨) 401 401 401 401 401 401 401
→ 6회째 응답이 다르다(423 ACCOUNT_LOCKED vs 401 INVALID_CREDENTIALS) → 가입 여부를 추론할 수 있다
참고: 가입 API도 중복 이메일에 409 DUPLICATE_EMAIL("이미 가입된 이메일입니다")을 준다 — 존재 확인 경로가 원래 하나 더 있다
판정: 잠금(S-02) 조치는 유효 · 계정 열거는 설계 한계로 점검서 §7 잔여 위험에 기록

## 관찰(조치 범위 밖 · 기록만)
- 잠긴 상태의 시도(423)는 감사 로그 줄이 남지 않는다 → BE-인증에 전달
- 해제 시각 문구에 마이크로초가 붙는다(15:42:01.940694) — 기능 영향 없음
- 잠금을 이용한 타인 계정 잠금(DoS)은 SPEC §7 잔여 위험
- 6회째 423/401 차이로 계정 존재 추론 가능(3-1) → 점검서 §7 잔여 위험 · `AuthService` 주석("계정 존재 여부를 노출하지 않는다")은 BE-인증에 정정 요청
